## 누락 재발 방지 기준

이전 실패 원인은 요약하면서 핵심 근거·회고를 삭제하고, 비교 대상 및 사례 단위를 혼동한 것입니다. 이후 페이지 수를 줄이거나 구성을 바꿀 때 아래 항목을 먼저 대조합니다.

1. 목차, 사례 번호·이름, 프로젝트 회고, 자료, 마무리가 연결되는가.
2. 각 사례의 문제·대안 비교·직접 구현·결과·검증·한계를 찾을 수 있는가.
3. 평균 응답시간의 세 단계와 DB 조회·캐시 적중 수치를 모두 보존했는가.
4. 원인 화면, SQL 2회 화면, 캐시 SQL 0회 화면, 투표 부하·집계 자료, Auth/User 변경 전후 이미지, 인증 흐름도, 협업 이미지 3개가 남아 있는가.
5. 삭제·통합은 중복 설명에 한정하고, 필요한 근거는 본문 또는 명확한 연결로 보존했는가.
6. 페이지당 큰 제목 하나, 본문·이미지 잘림 없음, 이미지 확대·목차·새로고침 복원을 실제 브라우저에서 확인했는가.
7. 최종 결과 뒤에 중간 검증으로 되돌아가지 않는가. 표에 검증 목적·단위·측정 대상이 있고, `0건`이 무엇을 세는지 명시했는가.
8. 이미지 설명이 실제 화면에 보이는 근거와 일치하는가. 원본 화면으로 확인할 수 없는 내용은 별도 기록으로 연결했는가.
9. 결과 페이지에서는 완료한 조치와 확인된 효과를, 회고에서는 그 경험으로 얻은 배움·판단 기준을 전달했는가. 회고의 ‘얻은 점’을 기능·성과의 재나열이나 앞으로 할 일로 대체하지 않았는가. 사용자의 최신 교정을 우선한다.
10. 하단선·넘침만 확인하지 않고, 본문 중간에 큰 빈 공간이 몰리는지도 확인했는가. `PageBottom`은 관련 설명을 묶는 용도로 사용하며 `margin-top:auto`로 강제로 밀어내지 않는다. 효과·한계·검증 범위처럼 연결된 설명은 함께 두고, 주 자료의 비율을 조정한다. 가로로 긴 이미지는 칸 높이만 늘려 빈 공간을 채우지 않는다.

### 수치와 근거의 해석

- [투표 Wiki](https://github.com/dbp-jack/FeedShop_Backend_Refactoring/wiki/피드-투표-동시성-개선)와 500·1,000·3,000명 원본 이미지에서 평균 응답시간 832.91ms·2,193.70ms·5,000.23ms를 확인했습니다. 표는 각각 **0.83초·2.19초·5.00초**로 통일했습니다.
- 성공 요청 합계 68,548·48,231·63,026은 개선 전후 수치가 아니라 별도로 실행한 부하 테스트의 처리 합계입니다. 실행 시간은 각각 2분 1초·2분·2분 1초로 비슷합니다. 요청 수가 비단조적으로 변한 원인을 시간 차이 등 하나의 요인으로 단정할 근거가 없어 요약 표에서 제거했습니다. 원본 테스트 이미지는 그대로 보존했습니다.
- HTTP 오류 0건과 DB 중복 저장 0건·집계 일치는 별개 지표입니다. 3,000명에서 평균 5초라는 측정값은 표에 유지합니다. 이후 사용자의 표현 교정에 따라 결과 설명은 실제 완료한 개선과 확인된 효과로 작성합니다.
- 3M Wiki의 서비스 경계 문서와 통합 테스트 보고서를 직접 확인했습니다. `0건`은 **User 모듈 소스의 Auth 패키지 import 수**이며 서비스 호출 수나 모든 의존성이 0이라는 뜻이 아닙니다.
- 권한 응답은 로컬 H2 환경에서 Gateway·Auth·User를 연결한 테스트 결과입니다. User API의 JWT 검증 제외, 권한 AOP·예외 처리 누락을 수정한 뒤 역할 변경 API에서 MASTER 200·HUB_MANAGER 403·미인증 401을 확인한 기록을 반영했습니다. 이번 포트폴리오 수정에서 프로젝트 테스트를 새로 실행한 것은 아닙니다.
